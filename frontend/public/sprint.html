Objetivo del Producto

Desarrollar una plataforma integral de gestión de la investigación estudiantil para la Unidad de Investigación de la FICCT - UAGRM, que centralice la administración de convocatorias (ferias, hackathones, concursos e investigación), la postulación y seguimiento de proyectos estudiantiles, la documentación académica colaborativa en tiempo real mediante WebSockets, la asistencia inteligente mediante chatbot, el análisis preventivo de contenido asistido por IA (RoBERTa), la evaluación formal por jurados y la certificación verificable con tecnología blockchain.

El sistema busca ordenar y transparentar todo el ciclo de investigación formativa de la facultad, eliminando la dispersión física o documental, facilitando el acompañamiento docente y dotando de inalterabilidad y prestigio a los reconocimientos académicos otorgados.

Requerimientos Iniciales

Requerimientos Funcionales por Módulo:

Módulo de Identidad, Usuarios y Control de Accesos

  • El sistema debe permitir el registro y creación de cuentas de usuario con nombre, correo electrónico institucional (@uagrm.edu.bo) y contraseña segura.
  • El sistema debe permitir el inicio de sesión seguro con autenticación mediante tokens JWT.
  • El sistema debe gestionar los roles de usuario: Administrador FICCT, Docente Supervisor, Jurado Evaluador, Estudiante y Visitante público.
  • El sistema debe ofrecer administración de cuentas (listar, buscar, activar, suspender usuarios y asignar roles).
  • El sistema debe permitir a los usuarios consultar y editar su perfil personal.

Módulo de Convocatorias y Eventos Académicos

  • El sistema debe permitir crear y parametrizar convocatorias clasificadas en: Ferias, Hackathones, Concursos y Convocatorias de Investigación.
  • El sistema debe permitir definir fechas de apertura, cierre de inscripción, tamaño de equipo y requisitos dinámicos de postulación.
  • El sistema debe gestionar los estados de las convocatorias: Borrador, Publicada y Finalizada.

Módulo de Portal Público y Repositorio

  • El sistema debe ofrecer una landing page pública accesible para visitantes y la comunidad sin inicio de sesión.
  • El sistema debe permitir buscar y filtrar convocatorias vigentes y proyectos aprobados por temática o palabra clave.
  • El sistema debe proveer una vista de consulta y verificación pública de certificados emitidos.

Módulos para Sprints Posteriores (S2 y S3)

  • Proyectos e Inscripciones: Postulación individual o en equipo de proyectos de investigación.
  • Documentación Colaborativa en Tiempo Real: Editor concurrente con WebSockets (STOMP), presencia en vivo y permisos granulares (Personal, Grupo, Grupo+Docente).
  • Asistente Virtual (Chatbot): Agente IA con capacidad de acción (crear convocatorias guiadas) y navegación a rutas del sistema.
  • Detector de Contenido IA: Servicio clasificador NLP (RoBERTa) para estimar porcentaje de probabilidad de texto generado por IA y resaltar fragmentos.
  • Supervisión Docente y Evaluación por Jurados: Observaciones de tutores y rúbricas estructuradas de veredicto.
  • Certificación Blockchain: Emisión de certificados digitales con hash inmutable y verificación QR.

Requerimientos No Funcionales:

  • Rendimiento: El tiempo de respuesta de las APIs REST en operaciones frecuentes debe ser inferior a 300 ms.
  • Seguridad: Almacenamiento de contraseñas hasheadas con BCrypt; endpoints privados protegidos mediante Spring Security con JWT.
  • Usabilidad: Interfaz sobria, funcional y responsive desarrollada en Next.js bajo la paleta institucional (definida en pantallas.html).
  • Disponibilidad: Arquitectura backend y base de datos con alta disponibilidad en red local/nube (99.5%).
  • Mantenibilidad: Arquitectura por capas en Spring Boot (Controller, Service, Repository, DTO) y código documentado.

Duración de los Sprints

El equipo ha decidido trabajar con sprints de 3 semanas de duración (21 días calendario / 15 días hábiles). Este tiempo se considera adecuado para planificar, desarrollar y revisar incrementos funcionales sin sobrecargar al equipo de 2 integrantes, permitiendo una entrega constante de valor al cliente y cumpliendo con las ceremonias formales.

Patrón de Desarrollo

Durante cada sprint, el equipo de desarrollo seguirá un patrón estructurado compuesto por las siguientes cuatro fases aplicadas a cada historia de usuario seleccionada en el Sprint Backlog:

  • Análisis: El equipo analiza en detalle las historias de usuario del sprint, comprendiendo su propósito, alcance y criterios de aceptación. Se identifican los módulos afectados, las posibles dependencias técnicas y las implicancias funcionales. También se revisan los datos necesarios, la lógica de negocio involucrada y los roles que interactúan con la funcionalidad.
  • Diseño: A partir del análisis, se define la solución técnica. Se diseñan las estructuras de datos necesarias, se determinan los endpoints o servicios a crear o modificar, y se maquetan las interfaces de usuario cuando corresponda. También se documentan las reglas de validación y se planifica cómo se integrará la funcionalidad con el resto del sistema.
  • Implementación: En esta fase se lleva a cabo el desarrollo del código, tanto en el backend como en el frontend. Se implementan los modelos, servicios, controladores y vistas, y se aplican las validaciones y reglas definidas. Todo el código se versiona en el repositorio y se realiza de forma colaborativa, cumpliendo con los estándares del equipo.
  • Prueba: Una vez implementada la funcionalidad, se realizan pruebas unitarias e integradas para verificar su correcto funcionamiento. Se validan todos los criterios de aceptación, se corrigen errores y se deja la funcionalidad lista para la revisión del Product Owner.

Modelos Iniciales

Modelo de Contexto Inicial: El sistema se relaciona con los siguientes actores y sistemas externos:

  • Administrador FICCT: Gestiona convocatorias, usuarios, roles, eventos y el panel público general.
  • Docente Supervisor: Revisa propuestas de investigación, da seguimiento académico y crea convocatorias.
  • Jurado Evaluador: Califica proyectos al cierre de un evento y registra actas de veredicto.
  • Estudiante Investigador: Se inscribe en actividades, gestiona su perfil y colabora en proyectos.
  • Visitante Público: Consulta convocatorias abiertas y busca certificados verificados sin requerir sesión.
  • Asistente Virtual (IA): Media entre el usuario y los módulos mediante lenguaje natural.

Definición de Criterios de Calidad

Siguiendo el estándar de ingeniería de software, el sistema adopta formalmente los 7 criterios de calidad para garantizar que el producto cumpla con los niveles requeridos de madurez técnica:

1. Correctividad
El sistema debe ejecutar correctamente todas las funciones especificadas en los requerimientos, sin comportamientos inesperados ni errores en los flujos principales.
  • El flujo de creación y registro de usuario debe validar correos institucionales únicos y contraseñas seguras sin fallos.
  • La autenticación con JWT debe validar credenciales y emitir tokens firmados con el rol exacto del usuario.
  • La parametrización de convocatorias debe registrar fielmente los requisitos dinámicos, tipos de evento y fechas límite.
  • El portal público debe listar el 100% de las convocatorias marcadas en estado "Publicada", omitiendo estrictamente los borradores.
  • El control de accesos basado en roles (RBAC) debe restringir las funciones administrativas únicamente a usuarios con rol ADMIN.
2. Eficiencia
El sistema debe hacer uso óptimo de los recursos computacionales del servidor y del cliente, minimizando los tiempos de procesamiento y respuesta.
  • El tiempo de respuesta de los endpoints REST en Spring Boot debe ser inferior a 250 ms en operaciones frecuentes.
  • La carga inicial de la aplicación Next.js y el renderizado del portal público no debe superar 1.5 segundos.
  • Las consultas a la base de datos PostgreSQL deben optimizarse con índices en campos de búsqueda (`email`, `convocatoria_id`, `estado`).
  • Las operaciones de hashing con BCrypt deben calibrarse (factor 10) para no sobrecargar la CPU del servidor.
3. Fiabilidad
El sistema debe operar de manera consistente y estable, recuperándose de fallos sin pérdida de datos críticos del usuario.
  • La plataforma debe garantizar una disponibilidad continua durante las sesiones operativas y evaluaciones.
  • Las transacciones en base de datos deben aplicar `@Transactional` en Spring Boot para garantizar atomicidad y consistencia.
  • Los errores no controlados deben ser capturados por un manejador global (`@ControllerAdvice`), retornando códigos HTTP estandarizados y mensajes amigables sin exponer trazas de error.
  • Manejo de reconexión transparente en el cliente si ocurre una pérdida temporal de conexión a la red.
4. Facilidad de Uso (Usabilidad)
La interfaz debe ser intuitiva, accesible y sobria para docentes, estudiantes y visitantes, siguiendo principios de diseño UX y la identidad visual institucional.
  • Un usuario nuevo debe poder completar su registro e iniciar sesión en menos de 2 minutos sin asistencia técnica.
  • Los formularios de convocatoria deben incluir previsualización interactiva en vivo que refleje el aspecto final en el portal.
  • Los mensajes de validación deben presentarse de forma clara junto al campo correspondiente en tiempo real.
  • La interfaz debe cumplir con principios de diseño responsive adaptándose a computadoras, tablets y teléfonos.
5. Facilidad de Mantenimiento
El código fuente debe ser modular, documentado y estructurado para facilitar la incorporación de nuevas funcionalidades y la corrección de errores.
  • El backend en Spring Boot debe seguir estrictamente la arquitectura por capas: Controller, Service, Repository, DTO y Mapper.
  • El frontend en Next.js debe estructurarse con componentes desacoplados y reutilizables bajo TypeScript con tipado estricto.
  • Cobertura de pruebas unitarias mínimas en la lógica de negocio del backend mediante JUnit 5.
  • El esquema de base de datos PostgreSQL debe administrarse con scripts DDL estructurados y versionados.
6. Seguridad e Integridad
El sistema debe proteger los datos personales y académicos contra accesos no autorizados, manipulación indebida o fugas de información.
  • Autenticación basada en JWT con algoritmo HMAC-SHA256, expiración configurada y almacenamiento seguro en el cliente.
  • Las contraseñas de los usuarios deben almacenarse hasheadas con BCrypt, nunca en texto claro en la base de datos.
  • Todos los endpoints privados deben protegerse mediante Spring Security validando el token y los roles autorizados.
  • Sanitización de entradas para prevenir inyecciones SQL (vía JPA Hibernate) y vulnerabilidades XSS.
7. Portabilidad
El sistema debe poder ejecutarse en diferentes plataformas y entornos con mínimas modificaciones de configuración.
  • La aplicación web cliente Next.js debe ser totalmente compatible con navegadores modernos: Chrome, Firefox, Edge y Safari.
  • El backend Spring Boot compilado en Java 17/21 debe ser ejecutable indistintamente en sistemas operativos Windows o Linux.
  • La base de datos PostgreSQL debe operar bajo estándares SQL estándar que faciliten su migración o respaldo hacia entornos de nube.

Retrospectiva de Sprint
Nombre del proyecto y número de retrospectiva: Sistema de Apoyo a la Investigación Estudiantil FICCT — Retrospectiva Sprint 1
Objetivos de la retrospectiva: Identificar qué funcionó bien en el equipo durante las 3 semanas del Sprint 1, qué dificultades se encontraron y definir compromisos de mejora para el Sprint 2.
Fecha y Hora: 21 / 09 / 2026   |   Hora: 19:30
Participantes
Daniel Quispe Choque & Brandon Vásquez
Discusión
¿Qué salió bien? • La decisión de definir el alcance del Sprint 1 de forma realista (registro, autenticación, usuarios y convocatorias) permitió entregar código probado sin estrés.
• Excelente complementariedad entre Spring Boot 3 y Next.js 14; el desacoplamiento por API REST facilitó que Daniel y Brandon trabajaran en paralelo.
• Apego estricto a los prototipos de pantallas.html, manteniendo consistencia en colores, bordes y tipografías.
• La duración de 3 semanas otorgó el tiempo adecuado para pruebas y ajustes sin interferir con otras asignaturas del semestre.
¿Qué no salió bien? [Problemas encontrados y resolución] • Problema: Se presentaron dudas iniciales en la configuración de CORS y cookies de autenticación entre Next.js (puerto 3000) y Spring Boot (puerto 8080).
• Solución: Se configuró formalmente un CorsConfigurationSource en Spring Security habilitando credenciales y orígenes locales.
• Problema: Al inicio se cargaron usuarios de prueba de forma manual, lo que consumió tiempo valioso en reinicios de base de datos.
• Solución: Daniel implementó un CommandLineRunner en Spring Boot para poblar automáticamente usuarios y roles al iniciar.
¿Qué debemos cambiar para mejorar en el Sprint 2? 1. Definir contratos de WebSocket anticipadamente: Documentar los tópicos STOMP (/topic/document/{id}) antes de programar el cliente colaborativo.
2. Preparar el microservicio de IA con antelación: Probar el modelo RoBERTa y los prompts del asistente en un script de prueba de FastAPI antes de conectarlo al frontend.
3. Mantener Dailies de 10 minutos al inicio de cada jornada para detectar a tiempo cualquier bloqueo técnico.
